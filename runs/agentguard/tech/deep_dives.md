## 1. Feedback-only adaptive attack loop (matched-budget)

- **Goal**: given a target agent, one defense configuration, and an attempt budget N, produce N rounds of injections that adapt to observed pass/fail outcomes only — the primary threat model (`BRIEF.md` Vocabulary).
- **Algorithmic approach**: AutoDojo's black-box LLM-driven iterative optimizer [S13], run inside (or adapted from) the AgentDojo environment [S1] — the closest direct match in the research. Structurally, this is the field's "in-context, live adaptation" category (`research/survey.md` §2): an LLM proposes an injection, observes the round's outcome, and refines within the same session, the same pattern PAIR [S30] and TAP [S31] established for chatbot jailbreaking and AutoDojo extended to agentic tool-use.
- **Inputs/outputs**: input — target agent harness, defense configuration (opaque to the attacker per feedback-only design), attempt budget N. Output — a sequence of N (injection, pass/fail) round records, an adaptation curve, and attempts-to-first-success.
- **Key design choice + rationale**: the attacker never learns defense identity, only round outcome — deliberately weaker information than AutoDojo's own published setup may assume, because BRIEF.md's Vocabulary treats feedback-only as the *representative* threat model (what a real external attacker actually gets), with white-box reserved as an explicit upper-bound comparison arm, never the headline.
- **Failure modes/fallbacks**: reward sparsity against a strong defense (most attempts blocked, thin adaptation signal) — the same problem PISmith's RL-based attacker documents for naive RL training [S18], relevant here even though AgentGuard's loop is in-context rather than RL-trained, because a defense that blocks >95% of early attempts still starves the optimizer of useful gradient-free signal. Fallback: budget the campaign to run to N regardless of early-round failure rate, and report attempts-to-first-success honestly (including "did not succeed within budget") rather than extending the campaign silently to force a success.

## 2. White-box upper-bound attack configuration

- **Goal**: produce an upper-bound comparison number — how much better a privileged attacker (one told the defense type up front) does against the same target/defense pair — never reported as the headline result.
- **Algorithmic approach**: GCG-style gradient-based suffix search [S29] adapted to agentic tool-use settings [S32], and TAP's black-box tree-search-with-pruning [S31] as the higher-performing alternative under realistic compute budgets, per the same agentic-adaptation study [S32].
- **Inputs/outputs**: input — target agent, defense identity/configuration (given, not inferred), attempt budget N (matched to the feedback-only arm for direct comparability). Output — a parallel round-record set, reported alongside but visually and structurally separated from the feedback-only headline metric.
- **Key design choice + rationale**: use TAP over GCG as the default white-box strategy where compute allows, because the agentic adaptation study found TAP "substantially outperforms GCG under realistic compute budgets" [S32] in this exact setting — a sourced, not assumed, choice.
- **Failure modes/fallbacks**: the same agentic-adaptation study found GPT-5 showed only ~5% ASR / 30% S@N against TAP [S32] — far below TAP's original >80% chatbot-jailbreak numbers [S31] — meaning this upper-bound arm may produce a *smaller* gap over the feedback-only arm against frontier-resistant models than the 2023-era literature implies. Fallback: report the white-box/feedback-only gap honestly per target-model generation rather than citing the older, larger gap as current.

## 3. Utility metric computation (AgentDojo-aligned)

- **Goal**: measure whether the target agent still completes the legitimate task a benign user asked for while a defense is active and an injection attempt is present — the metric that makes the security/usability trade-off visible (`BRIEF.md` Vocabulary).
- **Algorithmic approach**: AgentDojo's own utility definition [S1] — benign utility (fraction of tasks solved absent attack) and utility-under-attack (fraction of security cases where the agent solves the user task correctly with no adversarial side effects) — adopted verbatim rather than redefined.
- **Inputs/outputs**: input — the target agent's transcript for each round (tool calls made, final state). Output — per-defense utility scores (benign and under-attack), reported side by side with ASR, distinct from benign block rate.
- **Key design choice + rationale**: align to AgentDojo's definition rather than invent a new one, because `capability_table.md` flags that AgentGuard's campaigns are not bound to AgentDojo's fixed 629-case security-test suite — using the same definition, even over a different case set, keeps the metric legible to anyone who already knows AgentDojo's numbers, rather than adding a second, incompatible "utility" term to a field that already has one.
- **Failure modes/fallbacks**: utility numbers computed over AgentGuard's own campaign cases are **not numerically comparable** to AgentDojo's published utility numbers without an explicit bridging methodology (same caveat structure as the ASR-comparability note in `BRIEF.md`'s Vocabulary) — fallback is to always report AgentGuard's utility number as self-referential (this defense vs. that defense, same campaign) rather than implying direct comparability to AgentDojo's published baseline.

## 4. Defensive-prompting defense harness

- **Goal**: evaluate the cheapest, lowest-effort defense type — a system-prompt instruction pattern, not a separate model or policy engine — under adaptive pressure.
- **Algorithmic approach**: no single "best system" exists here — `capability_table.md` is explicit that this is a prompting pattern evaluated as one of several baselines inside AgentDojo/ASB/BIPIA [S1, S5, S6], not a product with its own name. AgentGuard's harness applies a configurable defensive-prompt template to the target agent's system prompt and evaluates the same round loop (item 1) against it.
- **Inputs/outputs**: input — the defensive-prompt text (customer-configurable, since this is the customer's actual deployed defense, not AgentGuard's invention). Output — round records identical in shape to every other defense harness, enabling direct cross-defense comparison.
- **Key design choice + rationale**: treat this as the first and cheapest defense type precisely because ASB's own static-evaluation baseline already finds an 84.30% average ASR across combinations [S5] — defensive prompting is expected to be the weakest link, and testing it first surfaces the sharpest, most legible result for a first-time user (Priya Nair's persona, `strategy/personas.md`).
- **Failure modes/fallbacks**: `capability_table.md` flags that no isolated, defense-specific adaptive-ASR number exists for defensive prompting alone — this is precisely the gap AgentGuard's own riskiest-assumption test (`BRIEF.md`) is designed to close, not a gap this harness can paper over with an assumed number.

## 5. Classifier-based detection harness

- **Goal**: evaluate a standalone classifier model that screens content for injection before it reaches the target agent.
- **Algorithmic approach**: wraps a classifier such as Meta PromptGuard 2 (86M or 22M variant) [S33, S34] as the defense-under-test; the harness intercepts each round's injected content, runs it through the classifier, and blocks or passes per the classifier's threshold before the target agent ever sees it.
- **Inputs/outputs**: input — classifier model choice/threshold (customer-configurable). Output — round records plus a classifier-specific signal (flagged/not-flagged) usable for a defense fingerprint (`BRIEF.md` Vocabulary).
- **Key design choice + rationale**: PromptGuard 2's self-reported numbers (97.5% recall at 1% FPR, 86M model [S34]) are *static*-evaluation numbers — the harness exists specifically to produce an adaptive-pressure number that does not yet exist in the published literature (`capability_table.md`'s explicit gap flag).
- **Failure modes/fallbacks**: self-reported robustness claims from a defense's own paper or vendor are precisely the kind of claim "The Attacker Moves Second" [S9] found collapses under genuine adaptive pressure for 12 other published defenses — the harness's fallback posture is to never cite PromptGuard 2's static numbers as a prediction of its adaptive-pressure result, only as a pre-test baseline to compare against.

## 6. Rule-based tool-call validation harness

- **Goal**: evaluate a policy-engine defense that gates tool calls at execution time based on a programmable privilege policy, independent of the LLM's own judgment.
- **Algorithmic approach**: wraps a policy language such as Progent [S38] — least-privilege, LLM-assisted policy generation, enforced at the tool-call boundary rather than inside the model's context.
- **Inputs/outputs**: input — the customer's policy configuration (which tool calls are permitted under which conditions). Output — round records plus a policy-violation log per attempt.
- **Key design choice + rationale**: this defense type sits structurally apart from the other three (prompting and classifiers both act on content; this one acts on the agent's *actions*) — deliberately kept as a distinct harness rather than folded into the classifier harness, because `capability_table.md` notes Progent's own self-reported claim (ASR reduced to 0% with preserved utility) is evaluated under presumably static or limited attack conditions, and the two defense mechanisms (content-screening vs. action-gating) plausibly fail differently under adaptive pressure.
- **Failure modes/fallbacks**: same self-reported-claim caveat as item 5 — Progent's 0%-ASR claim has "not been confirmed to be adaptively stress-tested by an independent party" (`capability_table.md`). Fallback: report Progent's (or any rule-based engine's) pre-existing published number alongside AgentGuard's own adaptive-pressure result, explicitly labeled by source, rather than silently replacing one with the other.

## 7. Matched-budget comparison / report aggregator — AgentGuard's actual contribution

- **Goal**: hold all four defense harnesses (items 4–6, plus baseline/none) to the *same* attempt budget N and the *same* attacker configuration, and produce one report — final-window ASR, attempts-to-first-success, campaign-average ASR, utility-under-attack, benign block rate, and adaptation curve, per defense, side by side.
- **Algorithmic approach**: not an attack or ML algorithm — a scheduling and aggregation layer. Round-management and retry/rate-limit bookkeeping follow PyRIT's orchestrator pattern [S59] (Microsoft's own multi-turn attack orchestration framework, used here for bookkeeping discipline, not for its attack strategies). Final-window ASR is computed over the last *k* rounds of each campaign specifically so early exploration failures — the expected shape of adaptation, not a defect — don't drag down the number that answers "does the attacker get there" (`ASSUMPTIONS.md`, "Decisions settled" section).
- **Inputs/outputs**: input — four completed (or in-progress, for continuous edge-high use) campaign round-record sets, one per defense, all run at the same N. Output — the Comparison Report: a per-defense table plus adaptation-curve plot, structured so cross-defense rows are directly comparable because the budget was matched by construction, not normalized after the fact.
- **Key design choice + rationale**: this is the one component `strategy/positioning.md` explicitly names as the actual open quadrant — "nobody has actually glued these two specific open pieces together and published the resulting cross-defense results yet." Everything upstream (items 1–6) is adopted prior art; this aggregation and equal-budget-enforcement layer is what turns four separate point measurements into one standing, reproducible comparison. Stated plainly: this is real but not deeply defensible engineering work (`strategy/positioning.md`), not a novel algorithm — the honest claim this whole pack is built to make.
- **Failure modes/fallbacks**: if one defense harness's campaign fails to complete at N (e.g., a classifier API outage mid-campaign), the aggregator must refuse to report that defense's row as comparable rather than silently truncating and comparing an N-round campaign to a partial one — an unmatched-budget comparison is worse than no comparison, per the same logic that invalidated the original adaptive-N-vs-static-1 test design (`BRIEF.md`, Riskiest assumption).

## 8. PyRIT-style round orchestration (cross-cutting, not a standalone stage)

- **Goal**: manage the mechanical concerns every campaign shares — model call retries, rate-limit backoff, per-round logging, and multi-turn conversation-state bookkeeping — so items 1–7 don't each reimplement this.
- **Algorithmic approach**: PyRIT's orchestrator-based pattern [S59] (Microsoft AI Red Team, released early 2024): an orchestrator LLM/process manages a dynamic multi-turn interaction (PyRIT's own attack strategies include Crescendo-style escalation) and logs each turn. AgentGuard reuses the *orchestration pattern* — turn management, retry/backoff, structured per-round logging — not PyRIT's attack strategies themselves, which are a different (and, per `research/competitors.md`, Microsoft-owned and free) product surface.
- **Inputs/outputs**: input — the raw sequence of model/tool calls each campaign round generates. Output — a structured, replayable per-round log usable both by the report aggregator (item 7) and by `tech/architecture/D08.md`'s observability layer.
- **Key design choice + rationale**: reuse a named, credible open pattern (PyRIT) for the boring, high-failure-surface plumbing (retries, rate limits, logging) rather than inventing bespoke orchestration — the plumbing is not where AgentGuard's differentiation lives (`strategy/positioning.md`), so it should be the least custom part of the system.
- **Failure modes/fallbacks**: orchestration bugs (a dropped round, a misattributed log entry) corrupt the matched-budget guarantee item 7 depends on — fallback is a completeness check before any campaign's round-record set is accepted into a Comparison Report (N logged rounds, not N attempted rounds).

## Recommended next 3

1. **Build item 7 (the aggregator) first, against stub/mocked harnesses for items 4–6**, since `strategy/positioning.md` identifies it as AgentGuard's one genuinely novel piece of engineering — de-risking it early is higher-leverage than polishing any single attack harness.
2. **Validate item 1 (the feedback-only loop) against AutoDojo's own published numbers on the same defense type before trusting AgentGuard's own re-implementation** — a reproduction check, not a new result, is the fastest way to catch an integration bug before it corrupts every downstream comparison.
3. **Do not build item 2 (white-box) before items 1 and 3–7 are solid** — it is explicitly an upper-bound comparison arm, not the product's headline mechanism, and `capability_table.md` already flags it as the least load-bearing of the eight items for AgentGuard's actual differentiation claim.
